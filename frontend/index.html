What is Banker's Algorithm?

The Banker's Algorithm (Dijkstra, 1965) prevents deadlock by ensuring each resource allocation leaves the system in a safe state — meaning there exists at least one sequence in which all processes can complete.

APPROVED
System remains in safe state. Resource allocated.
WAITING
Resources unavailable. Request queued.
REJECTED
Would cause unsafe state. Allocation denied.
RELEASED
Resource returned to available pool.

What is Deadlock Detection?

A deadlock occurs when a set of processes are each waiting for a resource held by another process in the set — creating a circular wait with no exit.

Detection Method: Resource Allocation Graph (RAG)
📌 Allocation edge: Resource → Emergency (resource is held by emergency)
📌 Request edge: Emergency → Resource (emergency is waiting for resource)
🔍 Run DFS on the graph — a back-edge means a cycle
⚠️ Cycle found → DEADLOCK DETECTED
✅ No cycle → System is safe
Deadlock scenario: Amb-1 is held by E-1, which waits for Bed-2. Bed-2 is held by E-2, which waits for Amb-1 → circular wait → deadlock.
Naming convention: Use R-Amb-1, R-Bed-2, R-Doc-3 for resources and E-1, E-2 for emergencies.

What is Starvation & Aging?

Starvation happens when a low-priority process waits indefinitely because high-priority processes always get resources first.

Solution: Aging
⏱ Each tick = one scheduling round passes
📈 Every 3 ticks waiting, effective priority is boosted by 1
🔁 Queue is re-sorted after each tick
✅ Eventually low-priority requests rise to the top
Priority scale: 1 = Critical (highest), 4 = Minor (lowest). Aging decrements the number, increasing urgency.
Starvation scenario: Set one request to priority 4 (Minor) and run 9+ ticks — watch it age up to priority 1 (Critical) and jump the queue.

What is a Semaphore?

A semaphore is a synchronization primitive that controls access to a shared resource by maintaining a counter of available permits.

Operations
🔒 acquire() — decrements permits; blocks if 0
🔓 release() — increments permits; unblocks a waiter
📊 Peak concurrent = max threads inside critical section at once
✅ Peak should never exceed the permit count
Hospital context: A semaphore with 3 permits = max 3 ambulances can simultaneously access the dispatch system, preventing race conditions.
What to expect: Peak Concurrent ≤ Permits = ✓ semaphore working correctly. If it were to exceed the permits, it would signal a bug in the synchronization logic.
